# BCH Dominion architecture

See the [offline game audit](docs/LOCAL_GAME_AUDIT.md) for current verification and the [transaction matrix](docs/BLOCKCHAIN_TRANSACTION_MATRIX.md) for the responsibilities of BCH, CashTokens, covenants, Nostr, and the game server.

`apps/web` serves the game HUD, browser input and presentation. Pointer and touch controls pan, zoom, and select independent city entities. The map renders the illustrated terrain beneath a territory canvas, city sprites, markers, and interaction controls. Battle motion reads recorded combat inputs and round events. The displayed motion does not calculate the winner.

`apps/game-server` serves HTTP JSON commands, a same-origin event stream, and static art. It authenticates each browser through a high-entropy session cookie. Clients submit action parameters with request identifiers. The game process serializes authoritative mutations with SQLite `BEGIN IMMEDIATE` and stores the world and command journal in the same transaction. Matchmaking, access checks, spending, and combat happen in `packages/game-engine`. `config` holds balance and economy parameters. A clock advances construction, research, army queues, visibility, political windows, and seasons. Server-Sent Events carry revisions and clients reload their own permission-filtered view.

`packages/chain-observer` separates intent construction, transaction parsing, network verification, and signing. The scheduler observes unique intent outputs and verifies active-chain evidence on Chipnet before credit. A confirmed action and its game result commit in one SQLite transaction. Outgoing payouts reserve confirmed outpoints and save the signed transaction before broadcast. Confirmed change is assigned to its original vault ledger. The live proof report captures chain events and authoritative game outcomes.

`packages/game-engine/government.mjs`, `diplomacy.mjs`, and `political-trade.mjs` keep authoritative government, conflicts, treaties, councils, and shipments in the existing world document. The simulation clock resolves dated events even when players are offline. The same combat and territory eligibility rules govern coalition campaigns, military escorts, treaty permissions, and political restoration. Battle inputs, private offers, and political intelligence cross permission-filtered views; the public archive reveals resolved records.

`apps/game-server/politics-protocol.mjs` bridges ratified terms and confirmed UTXOs without putting the game state in a contract. Political charges reuse the normal payment allocator, while `packages/chain-observer/political-escrow.mjs` constrains compensation to an exact principal and one of the agreed wallet destinations. SQLite journals funding, settlement, and proof records; the signed spend is stored before broadcast. A separate optional CashTokens issuer journals charter minting independently of the territory issuer. The archive serves JSON at `/api/public/politics` and a browser view at `/verify/politics`. See [political mechanics and verification](docs/POLITICAL_MECHANICS.md).

`packages/game-engine/stats.mjs` derives order previews and projected upgrades from the same rules that execute them. Attack preparation only receives public terrain, current authorized allied or scout observations, and the player's own orders. Settlement policies and combat field rules are versioned separately so saved receipts, claims, and battle replay inputs remain reproducible.

`packages/decentralized-identity` verifies portable links between separate BCH and Nostr keys, key history, discovery responses, and authentication proofs. `apps/game-server/identity.mjs` binds nonce use to SQLite sessions. Account progression remains in the game save; it is not signed by a blockchain or relay. The offline preview runs with in-memory state and blocked BCH transports.

The local deployment uses one Node process and SQLite. The saved atlas preserves core coordinates and opens connected regions when available plots are exhausted. The browser renders the current region within its camera bounds. Initial and refreshed game-state responses use gzip when the client accepts it and the snapshot is large. In a 1,000-registration fixture, the same full state was 3,743,076 bytes uncompressed and 139,923 bytes on the wire with gzip.

The world remains a single JSON document. The large admission test measures serialized SQLite writes over 64 loopback connections. Sustained play with 1,000 active clients still needs a narrower state projection and load verification. SQLite and the project’s durable leases assume a single app replica. Browser synchronization uses SSE with HTTP commands.
