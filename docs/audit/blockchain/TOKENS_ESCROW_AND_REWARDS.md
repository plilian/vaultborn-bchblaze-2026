## Token and game authority

`packages/chain-observer/territory-token.mjs:20` normalizes event kind, version, territory, controller, holder, related transaction, and optional expiry. `territoryCommitment` binds the canonical event digest in an immutable NFT commitment and OP_RETURN. Issuance requires the live minting baton, returns one baton to its issuer, and checks its own transaction in the BCH VM. `validateTerritoryIssue` validates the exact authorized recipient, commitment, carrier amount, anchor, and baton spend.

The journal in `packages/chain-observer/territory-assets.mjs` persists events and signed transactions before broadcasting, serializes active issuance, and retains the same plan through retry/restart. With only the issuer public key it can verify known asset records but cannot mint new ones. The issuer's private key controls the minting baton: chain rules alone do not independently attest that a particular game event happened, or stop the holder of that minting authority from creating semantically duplicate collectibles using a different transaction. Application event IDs, related receipts, and the issuance journal provide that policy. This is an explicit trusted-issuer boundary, not a demonstrated outside-user minting exploit.

Game control does not follow a token sale. The public asset expressly reports `game-controlled; collectible transfer does not change territory control` (`territory-token.mjs:233`). Lease expiry closes extraction in the game while the historical lease NFT remains spendable in its owner's wallet. Political charter transfer does not transfer a treaty, council vote, or kingdom. New CashToken-based commander or item benefits were not inferred from the existence of a proof NFT.

## Current season mechanics and custody

The authoritative archive is created by the game at season rollover (`packages/game-engine/economy.mjs:93`), filtering NPCs from archived player rankings. The ledger selects the latest finalized season and admits positive-score, registered seats; it requires at least two eligible participants except for already committed legacy payout windows (`apps/game-server/ledger.mjs:85`). It does not accept a caller-supplied winner proof.

The claim window lasts one season. Confirmed sponsor funding from the target or an earlier season is eligible; future-season funding is excluded. Current prize rules reserve 15% and distribute the award base over ranks 1–5 at 40/25/15/10/10. The first committed claim fixes that base. Before commitment the base can be reduced to make the leading payout fundable within the 32-input planner, leaving excess for later seasons. A rank is therefore not an unconditional promise of a spendable payout. Awards below 600 sats, unclaimed/expired awards, unused reserve, and unavailable or fragmented funds follow the existing eligibility/carry-forward rules.

`planPayout` recalculates eligibility and current sources, requires the player's verified receiving address for prizes, and blocks concurrent pending payouts (`ledger.mjs:365`). `payout` checks consent and quote values, signs and stores the reservation before broadcast (`ledger.mjs:404`). A consumed/committed award cannot be claimed again through the application. The sponsorship Development allocation happens once in the original incoming transaction, not at each rollover or payout.

Actual season funds remain under the configured operator's treasury scripts. The database, archived ranking, and operator authorization determine who is paid. There is no integrated independently signed winner attestation or permissionless contract claim in this UI/API path. Removing the operator key disables new claims. Generic fixed-recipient vouchers now have real Regtest spend evidence, but that proves a distinct template, not migration of the active pool. The contract report includes this trust/integration finding.

## Political compensation and recovery

The integrated political contract is stronger than an ordinary operator-owned deposit: it fixes the payee or payer script, exact principal, and output shape. The operator may release the principal or return it, while the original payer can independently recover after an absolute locktime using the payer key. The six-hour application recovery time is not a deadline that makes the release branch invalid; conflicting valid spends race for the same outpoint. The pre-existing Regtest receipts prove the independent timed branch and rejection before consensus finality.

The standard supported plan commits a 650-sat fee reserve. The current refund CLI and signer accept only the exact quoted funding amount. Invalid-amount payments and future fee pressure therefore need separate recovery planning; they must not be described as automatically recoverable through the supplied CLI. See the misfunding/recovery discussion in `CONTRACTS_AND_SECURITY.md`.

### TR-01 — Medium — Independent political returns are not recognized without the operator signer

- **Status:** FAIL (new audit-only reproduction); on-chain user recovery itself remains valid.
- **Location:** `apps/game-server/politics-protocol.mjs:112–116`; caller `apps/game-server/ledger.mjs:538`.
- **Impact:** A server running with the treasury public key and observer but without its private signing key cannot observe an independently completed payer return. Escrow/treaty state and the reported locked balance stay `funded` / awaiting settlement until signing configuration is restored. This does not let an outsider steal the returned BCH.
- **Reproduction:** Supply a mature credited escrow and a read-only chain with `payoutsEnabled:false` whose observer can return a confirmed payer-refund spend. Call `reconcile()`. The observer is called **zero** times and stored status remains `funded`.
- **Evidence:** [Gap probe results](evidence/tokens-gap-results.json), generated by `node var/audit-blockchain/tokens-audit.mjs`. This is a controlled, offline dispatch test and is not a new on-chain refund.
- **Cause:** The signer availability guard precedes both read-only spend discovery and signing work.
- **Recommended future fix:** Permit verified spend observation and reconciliation without private signing capability; guard only transaction creation/signing. Add a read-only restart integration case around the existing independent-return contract test. No fix was made.

### TR-02 — Low — Valid NFT ownership becomes unresolved at traversal and address-history bounds

- **Status:** FAIL (bounded-monitor limitation, new audit-only reproduction).
- **Location:** `packages/chain-observer/territory-token.mjs:198`, `:205`, and `:230`.
- **Impact:** The game cannot identify the current owner of an otherwise valid immutable NFT after sufficient transfers or address activity. It returns an explicit unknown state rather than falsely assigning ownership. The token remains spendable and game control is unaffected.
- **Reproduction:** Build valid synthetic NFT transfers, verify their scripts in the BCH VM, and provide a deterministic read-only history. Fifteen transfers resolve `unspent`; sixteen yield `traversal-limit` with `current:null`. In another probe, one real spender placed after 256 unrelated history entries yields `unresolved`.
- **Evidence:** [Gap probe results](evidence/tokens-gap-results.json). All listed hashes in that file are **synthetic fixtures, not Chipnet TXIDs**. Real seven-collectible history verification remains PASS separately.
- **Cause:** The initial ownership check consumes one of 16 loop iterations, and only the first 256 candidate history entries are examined. There is no continuation cursor or persisted verified traversal head.
- **Recommended future fix:** Add bounded pagination/continuation and persist a verified last outpoint, preserving explicit uncertainty and resource limits. Do not silently assume a holder when a bound is reached. No fix was made.
